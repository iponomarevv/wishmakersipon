# Безопасность Supabase в Wishmakers

## 🔒 Как используется Supabase

### Текущая архитектура:

1. **Серверная часть (Vercel Functions):**
   - Использует `SERVICE_ROLE_KEY` для записи и чтения
   - Ключи хранятся в **Environment Variables** Vercel (не в коде)
   - Все запросы к Supabase идут **только через API endpoints** (`/api/lists/*`)

2. **Клиентская часть (React):**
   - **НЕ использует Supabase напрямую**
   - Все запросы идут через `apiClient.ts` → API endpoints
   - Никакие ключи Supabase не попадают в клиентский код

3. **База данных:**
   - Таблица `public_lists` с RLS (Row Level Security)
   - Текущие RLS policies: **полный публичный доступ** (для MVP)

## ✅ Что безопасно:

1. **Ключи защищены:**
   - `SERVICE_ROLE_KEY` используется **только на сервере** (Vercel Functions)
   - `ANON_KEY` не используется в клиенте (только на сервере как fallback)
   - Ключи хранятся в Vercel Environment Variables (зашифрованы)

2. **Нет прямого доступа из клиента:**
   - Клиент не может напрямую обращаться к Supabase
   - Все запросы проходят через API endpoints
   - API endpoints контролируют доступ

3. **HTTPS:**
   - Все соединения идут по HTTPS (Vercel автоматически)

## ⚠️ Риски для MVP (приемлемы):

1. **Публичный доступ к спискам:**
   - Любой, кто знает ID списка, может его прочитать
   - Это **нормально для MVP**, где все списки публичные

2. **Нет аутентификации:**
   - Любой может создать/изменить/удалить список
   - Для MVP это приемлемо, но для продакшена нужно добавить авторизацию

3. **Нет rate limiting:**
   - Нет ограничений на количество запросов
   - Vercel имеет встроенные лимиты, но можно добавить дополнительные

## 🚨 Что нужно исправить для продакшена:

### 1. Добавить аутентификацию пользователей

```typescript
// В API endpoints добавить проверку пользователя
const userId = req.headers['x-user-id']; // Из Telegram WebApp
if (!userId) {
  return res.status(401).json({ error: 'Unauthorized' });
```

### 2. Ограничить доступ к спискам

```sql
-- В Supabase изменить RLS policies:
CREATE POLICY "Users can only modify their own lists" ON public_lists
  FOR ALL
  USING (data->>'ownerId' = current_setting('request.jwt.claims', true)::json->>'sub')
  WITH CHECK (data->>'ownerId' = current_setting('request.jwt.claims', true)::json->>'sub');
```

### 3. Добавить валидацию данных

## 📊 Текущий уровень безопасности: **MVP (приемлемо)**

Для MVP (минимально жизнеспособного продукта) текущая реализация **безопасна**:
- ✅ Ключи не попадают в клиент
- ✅ Все запросы идут через API
- ✅ HTTPS используется автоматически
- ⚠️ Публичный доступ к спискам (по дизайну для MVP)

## 🔐 Рекомендации:

1. **Для MVP:** Текущая реализация подходит
2. **Для продакшена:** Добавить:
   - Аутентификацию пользователей
   - Ограничение доступа к спискам
   - Валидацию данных
   - Rate limiting
   - Мониторинг

## 🛡️ Защита от основных атак:

- ✅ **SQL Injection:** Защищено (Supabase использует параметризованные запросы)
- ✅ **XSS:** Защищено (React автоматически экранирует)
- ⚠️ **CSRF:** Частично защищено (CORS настройки Vercel)
- ⚠️ **DDoS:** Защищено базовыми лимитами Vercel (можно улучшить)

## 📝 Итог:

**Текущая реализация безопасна для MVP**, но требует улучшений для продакшена. Основные риски связаны с публичным доступом к спискам, что является частью дизайна MVP.
